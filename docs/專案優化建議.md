# 專案優化建議

檢查日期：2026-11-12
範圍：`app/`、`src/`、`tasks/`、`bot/`、`frontend/src/`、`conf/`、`docker/`、compose 檔。包含還沒 commit 的配裝模擬與 JSON 資料庫快取。
這份文件只列建議，沒有改任何程式。

每一項都標了依據：

- **已查證**：在程式碼裡 grep 或實際跑過，括號裡是數字或檔案位置。
- **推測**：依程式結構判斷，沒有在正式環境量過，動手前要先確認。

跟 2026-08-21 的《專案審查報告.md》不重複：那份著重安全性與資料正確性，這份只看 UI、功能、資源利用、重複程式。

## 一、UI

### U1. 玩家頁 15 個分頁，桌機已經折成兩行

**已查證**：`utils/playerTabs.js` 有 15 個主分頁；1600 px 寬的截圖上分頁列折成兩行（工具網站、個人資料掉到第二行）。

建議分成四組，分頁列只放組名，組內用現有的下層分頁（`subTabs`）機制：

| 組 | 內含 |
|---|---|
| 倉儲 | 倉庫、物品、藍圖、查詢持有資訊 |
| 艦船 | 艦隊、配裝模擬、貨艙網格 |
| 航行 | 航線、任務、礦物 |
| 工具 | LOG 解析、酬勞分配、中文轉碼、工具網站 |

個人資料維持獨立。後台的分頁順序／開放設定、玩家自己的顯示勾選、舊網址 `?tab=` 都要對應到新結構，這是主要工作量。

### U2. 選船介面有三套

**已查證**：`ShipPicker.vue`（航線）、`CargoLoader.vue`、`LoadoutSimulator.vue` 各自寫了一份船名搜尋、「我的機庫優先」排序和船名顯示。

建議統一用 `ShipPicker`，加一個「機庫的船列成按鈕」的選項。三個地方的操作方式會一致，之後改搜尋規則只改一處。

### U3. 配裝模擬、艦隊、貨艙網格沒有互通

三個功能都以「一艘船」為單位，但現在各走各的：

- 配裝模擬做好的配裝要自己複製連結，再到艦隊「編輯」貼上。建議加「存到我的艦隊」按鈕，直接寫進那艘船的配件網址。
- 艦隊列表每艘船建議加「配裝」按鈕，直接帶著那艘船開配裝模擬（比照現在的「網格」按鈕）。
- 艦隊裡存的本站配裝連結可以直接顯示摘要（DPS、護盾），不用點開。

### U4. 提示訊息消失的時間不一致

**已查證**：8 個檔案各自用 `setTimeout` 清訊息，時間有 1.5、2、3、4、5、6 秒六種。

建議做一個共用的 `useFlash(毫秒)`，全站統一成兩種：「已複製」這類 1.5 秒，操作結果 5 秒。

### U5. 配裝模擬頁面太長

**已查證**：Perseus 在 1600 px 寬時整頁約 2300 px 高；手機上要先滑過三張統計卡才看得到掛點。

建議：

- 每個掛點分區可以收合，預設只展開武器類。
- 手機上把「持續 DPS／護盾 HP／電力」做成黏在頂部的一行摘要，統計卡收進可展開的區塊。
- 更換視窗在手機上每筆佔半個螢幕，「其他」數值預設收起來。

### U6. 後台與玩家頁的資料列表各做各的

**推測**：後台有 `ItemListView`、`VehicleListView`、`CommodityListView`、`MissionListView`、`FactionListView`、`BlueprintListView` 加上通用的 `DataBrowserView`；玩家頁另有 `ItemDataBrowser`、`VehicleDataBrowser`、`BlueprintMasterBrowser`、`MissionBrowser`。結構都是「搜尋卡＋排序表格＋分頁＋詳細」。

這是大工程，不建議現在整併。之後新增列表時先看能不能用 `DataCollectionTable`，不要再加第 12 個。

## 二、功能

### F1. 配裝模擬的三個小缺口

1. **發電格數沒有保底**（已查證，`utils/loadoutPower.js` 的 `generation()`）：發電機在配件主檔查不到時，發電格數會算成 0，整張電源卡顯示超載。現有 281 艘太空船沒有這個情況，但上游更新後可能出現。應該退回船本身的預設格數。發電機 EM 同理。
2. **頁面開著時點另一個分享連結不會切換**（已查證，只在第一次載入時讀網址）。
3. **切到別的分頁再回來，網址上的船與配裝參數不會補回去**，要換一次配件才會補。

### F2. 版本快照只寫不讀

**已查證**：`tasks/scdata_sync.py` 每次同步都寫 `item_master_versions` 等 5 個 `*_versions` 資料表；全專案只有後台「資料瀏覽」會列出來，沒有任何功能讀它。

二選一：做一個用得到它的功能（例如「這個版本改了哪些物品數值」），或停止寫入並清掉。

### F3. 同一份資料有兩個來源

| 資料 | 來源一 | 來源二 | 建議 |
|---|---|---|---|
| 量子引擎數值 | `item_master` 的 `qd_*`（Wiki API） | `ship_item_master`（scunpacked） | 航線改讀 `ship_item_master`，配裝模擬和航線算出來的航程才會一樣 |
| 船的量子參數 | `ship_nav_master` | `ship_loadout_master` | 兩個都從 `ships.json` 來，併成一個資料表、一個同步項目 |
| 貨艙 | `vehicle_master.cargo_grids`（Wiki） | `cargo_grid_master`（sc-cargo.space） | 確認前者還有沒有人用，沒有就不存 |

**已查證**前兩列（`src/scdata.py` 的 mapper）；第三列的使用狀況沒有逐一追。

### F4. 查詢持有資訊要打三支 API 再自己合併

**已查證**：前端分別呼叫物品（`/inventory/search`）、藍圖（`/blueprint/holders`）、船艦持有，再在 `MyPlayerView.vue` 合成一張表。相關的查詢端點共有 6 支（`/item/search`、`/item/match`、`/inventory/search`、`/inventory/where`、`/player/search`、`/blueprint/holders`）。

建議加一支 `/player/holdings?q=&kind=`，後端一次回合併好的結果。前端可以拿掉合併三份結果的邏輯，Discord 機器人和 AI 問答也能共用。

### F5. AI 問答只有 Discord 用得到

後端 `src/ai/ask.py` 已經跟介面無關。玩家頁加一個問答框的工作量很小，限流和紀錄都現成。要不要做看需求。

## 三、資源利用

### R1. 玩家站沒有開 gzip

**已查證**：`conf/nginx-web/default.conf` 沒有任何 gzip 設定，`docker/Dockerfile.web` 用的 nginx 官方映像預設是關的。另一個 `conf/nginx/nginx.conf` 有開，但那是 API 前面的 nginx。

玩家頁主要的 JS（`MyPlayerView`）打包後 447 kB，gzip 後 143 kB（實際 build 的數字）。如果前面有 Cloudflare 會代為壓縮，直接連 8090 埠就是原始大小。

建議在 `conf/nginx-web/default.conf` 加上 `gzip on` 和 `gzip_types`（JS、CSS、JSON、SVG）。

### R2. 玩家頁一次載入全部分頁

**已查證**（`views/MyPlayerView.vue`）：

- 靜態 import 31 個元件，全部打進同一個 447 kB 的檔案。
- 24 個分頁面板都用 `v-show`，進頁面時全部建立。
- 不管開哪個分頁，一進來就載入庫存、庫存紀錄、藍圖三支 API。

建議：

- 重的元件改 `defineAsyncComponent`：配裝模擬、航線（含 3D 星圖）、合約分配、礦物、貨艙網格、LOG 解析。
- 面板改成「第一次切到才建立，之後保留」。
- 庫存紀錄、藍圖改成切到該分頁才載入。

只看倉庫的人就不用下載配裝模擬和 3D 星圖的程式。

### R3. gunicorn worker 數跟記憶體上限不搭

**已查證**：`gunicorn.py` 預設 `CPU 數 × 2 + 1` 個 sync worker（`conf/config.ini` 裡 `WORKERS` 是註解掉的）；`docker-compose.api.yml` 把 API 容器限制在 256 MB。

**推測**：每個 worker 各自持有一份航線世界快取（`src/models/nav.py` 的 `_cache`）和翻譯快取（`src/models/translation.py`）。4 核主機會開 9 個 worker，很可能超過 256 MB。沒有實際量過記憶體。

建議在 `config.ini` 固定 `WORKERS=2`、`WORKER_CLASS=gthread`、`THREADS=4`。快取份數從 9 份降到 2 份，同時處理的請求數差不多。

### R4. 主檔的 `raw` 欄位

**已查證**：`src/scdata.py` 有 10 個 mapper 把上游整包原始資料存進 `raw`；查詢時只有 6 處用 projection 排除它；`ItemMaster.get()`（`src/models/item.py:43`）沒有 projection，每次都把整包讀出來。

建議：

- 短期：`get()` 加預設 projection 排除 `raw`，需要的地方再明確要求。
- 長期：`raw` 搬到獨立的資料表（例如 `item_master_raw`），主檔變小，列表查詢和索引都受益。

### R5. 同步用的 worker 開太多行程

**已查證**：`docker-compose.worker.yml` 預設 `--concurrency=4`，記憶體上限 768 MB。同步任務有鎖，同時間實際只會跑一輪。

建議預設改成 2。JSON 改存資料庫之後，單一任務的記憶體峰值已經降下來（`ships.json` 實測從 248 MB 降到 143 MB）。

### R6. 有些資料表沒有保存期限

**已查證**（`src/mongo.py`、`tasks/scheduled.py`）：

| 資料表 | 現況 |
|---|---|
| `logs` | 每天清 90 天前的 |
| `ai_logs` | 30 天自動過期 |
| `login_failures` | 1 天自動過期 |
| `sync_runs` | **沒有清理** |
| `inventory_log` | **沒有清理** |
| `scdata_json_rows` | 每個檔案留最近兩版（約 70～80 MB） |

建議 `sync_runs` 加 90 天的 TTL 索引。`inventory_log` 是玩家看得到的庫存紀錄，要先決定保留多久（例如一年）再加。JSON 快取可以考慮只留一版，省一半空間。

### R7. 配裝模擬的 API

- **已查證**：`loadout.ships()` 每次請求都讀整個 `vehicle_master` 來排序。可以比照航線加 5 分鐘快取。
- **已查證**：更換武器視窗一次抓回約 390 kB（武器＋砲塔兩類）。可以只回列表要用的欄位。
- 配裝資料一天才同步一次，三支 API 都可以加 `Cache-Control: private, max-age=600`。

### R8. 測試跑一輪要 6 分多鐘

**已查證**：全套 1065 個測試跑 378 秒，光 `tests/test_permissions.py` 就佔 103 秒。

建議裝 `pytest-xdist` 用 `-n auto` 平行跑；`test_permissions` 看能不能讓參數化的案例共用登入 token。

## 四、重複功能簡化

### D1. 前端「抓 API 再解 JSON」的樣板

**已查證**：`await res.json().catch(() => null)` 加上 `res?.ok && body?.success` 的判斷，在 47 個檔案出現 111 次。

建議在 `api/` 加一個 `getJson(fetcher, url, options)`，回傳 `{ ok, data, message }`。新程式先用，舊的分批換。

### D2. localStorage 讀寫樣板

**已查證**：15 個檔案、63 處 `localStorage.getItem／setItem`，每處都包一層 try/catch 和 JSON 解析。

建議做 `useStoredState(key, 預設值)`，回傳會自動存回去的 ref。

### D3. 數字與名稱格式化

**已查證**：

- `toLocaleString(` 在 26 個檔案出現 47 次，`utils/navFormat.js` 已經有 `fmtNum`。
- 「中文名（英文名）」的船名顯示有 3 份：`navFormat.js`、`CargoLoader.vue`、`LoadoutSimulator.vue`。
- 配件種類的中文名稱表有 2 份：`LoadoutSimulator.vue`、`LoadoutPowerCard.vue`。

建議統一用 `navFormat.js` 的版本；種類名稱表搬到 `utils/loadoutCalc.js`。

### D4. 後端下載重試迴圈有三份

**已查證**：`src/scdata.py` 裡 `get_json()`、`fetch_json_url()`、`fetch_translation_ini()` 各有一份幾乎一樣的「429／5xx／連線錯誤重試」迴圈。

建議抽成一個 `_request_with_retry(client, url, on_response)`，三個函式只留各自的內容檢查。之後調整重試規則只改一處。

### D5. 同步的「低於 80% 不下架」保護有四份

**已查證**：`tasks/scdata_sync.py` 有 4 處各自寫「這次筆數低於原本的 80% 就不下架」加上下架的 `update_many`。

建議抽成 `_retire_missing(collection, run_id, seen, scope)`。

### D6. 配裝模擬內部的重複

**已查證**：

- 「同時運作的護盾取最強幾個」在 `loadoutCalc.js` 和 `loadoutPower.js` 各一份。
- `src/models/loadout.py` 的 `ships()` 幾乎照抄 `src/models/nav.py` 的 `ships()`（同名船只留一筆），還直接用了 nav 的私有常數 `_VARIANT_RE`。

建議各抽成一個共用函式。做了 F3 的資料表合併後，第二項會自然消失。

### D7. 檔案太大

**已查證**（行數）：

| 檔案 | 行數 | 建議 |
|---|---|---|
| `frontend/src/views/MyPlayerView.vue` | 3156 | 倉庫、藍圖、艦隊、查詢持有資訊各拆成一個元件，跟 R2 一起做 |
| `app/player/view.py` | 1551（40 支路由） | 依功能拆成玩家帳號、玩家資料、後台管理三個檔 |
| `src/scdata.py` | 1511 | 下載與重試、Wiki mapper、scunpacked mapper 分開（配裝已經先拆出 `scdata_loadout.py`） |
| `README.md` | 1634 | 同步來源表、資料表清單搬到 `docs/`，README 只留安裝與連結 |

### D8. 沒用到的程式與依賴

**已查證**：

- `FieldHint.vue`、`FilterBar.vue`、`SfTreeHead.vue` 三個元件沒有任何地方 import。`CLAUDE.md` 還提到 `FieldHint`，刪之前確認一下，文件要一起改。
- MySQL 整套沒在用：`src/mysql.py` 沒有人 import，`requirements.txt` 有 `PyMySQL`，compose 裡有 mysql 服務（預設不啟動）。
- `app/sample/` 是範本留下來的範例路由，還註冊在 `/sample`。
- `CLAUDE.md` 的目錄結構速查還是範本的樣子（`Template-PythonFlaskAPI/`），沒有反映現在的 `app/` 藍圖。

## 不建議動的地方

檢查過、覺得現在就夠好的：

- **同步排程頁的輪詢**：已經是同步中 3 秒、閒置 15 秒，不用改。
- **前端依賴**：只有 Vue、Pinia、vue-router、Bootstrap 五個套件，3D 星圖和貨艙是自己用 canvas 畫的，沒有可以拿掉的大套件。
- **配裝模擬的前端計算**：最複雜的船（Polaris，142 格掛點）換一次配件重算不到 1 毫秒，不需要優化。
- **靜態檔快取**：`/assets/` 已經設 30 天不可變快取。
